# 補充報告 #2：machine2 持續 DAQ_ERROR 的根因與解法

對應使用者問題：「為什麼 motor2 測試中一直 DAQ_error 但是之前用 request-example 就沒事？有什麼解決方法嗎？」

---

## 1. 結論先行

| 項目 | 結論 |
|---|---|
| 是不是 pipeline 的鍋？ | **不是**。`request-example.py` 也炸 |
| 真正瓶頸 | I-8014W **Magic Scan 多通道 aggregate sample rate 上限約 80–90 kS/s** |
| 為什麼之前 request-example 偶爾過？ | 12 ch × 10 kHz = 120 kS/s 在邊界外，第一次跑成功只是 OS / 網路 buffer 暫時順暢，並非穩定 |
| 解法 | machine2 RATE 由 10 kHz → 5 kHz（aggregate 60 kS/s 安全帶），並在 pipeline 加 err=203 自動重試 |
| 副作用 | machine2 Nyquist 從 5 kHz → 2.5 kHz；50/60 Hz 基波與低次諧波不受影響，僅 VFD 載波頻率識別精度下降（不是 ML target） |

---

## 2. 診斷過程

### 2.1 對照組實驗

直接以原版 `request-example/request-example.py`（PAC_IP = 192.168.1.13、CH=12、RATE=10000、SEC=10、RTU1=1 RTU2=2）對 machine2 跑：

```
Sending command: START_CAPTURE CH=12 RATE=10000 SEC=10 RTU1=1 RTU2=2
=== HEADER ===
status: 1
...
errorCode: 203
PAC returned error. No payload will be saved.
```

**「已知好用」的 reference client 也回 errorCode=203**。同時對 machine1 跑等價條件（CH=4 RATE=10000）成功 → 排除網路、agent 共用 binary、home PC 端問題。**問題集中在 machine2 處理 12 通道高速取樣的能力。**

### 2.2 取樣率掃描

在 machine2 上掃不同 CH × RATE 組合，每次間隔 5 秒讓 I-8014W 喘息：

| CH | RATE (Hz/ch) | aggregate (kS/s) | 結果 | err |
|---|---|---|---|---|
| 12 | 10000 | 120 | ❌ FAIL | 203 (FIFO overflow) |
| 12 |  8000 |  96 | ❌ FAIL | 203 |
| 12 |  5000 |  60 | ✅ OK   | 0 |
|  8 | 10000 |  80 | ✅ OK   | 0 |
| 12 | 10000, SEC=5 | 120 | ❌ FAIL | 203 |

**邊界**：80 kS/s 過、96 kS/s 不過 → machine2 的 I-8014W Magic Scan 在多通道下實測 sustainable aggregate 上限約 **80–90 kS/s**。

### 2.3 對照 datasheet

[I-8014W datasheet](../spec/I-8014W類比輸入模組/8014_9014_en.pdf) 標稱：

| Mode | Rate |
|---|---|
| Single Channel Pacer Mode | 250 kS/s |
| Single Channel Polling Mode | 45 kS/s |
| 8 Channels Polling Mode | 25 kS/s |
| Multi-channel Magic Scan | (datasheet 未明列，但 agent 用此模式) |

實測 80 kS/s 落在「8 ch polling 25 kS/s」與「single ch pacer 250 kS/s」之間，符合 Magic Scan 多通道下的合理區間（介於兩者之間）。**12 通道 × 10 kHz/ch = 120 kS/s 確實超過 sustainable 範圍**。

### 2.4 為什麼第一次成功？

`run_once` 在 17:04:56 跑 12 ch × 10 kHz 一次成功（status=0、payload=2,400,000B）。之後所有相同條件嘗試（含 request-example.py）皆失敗。

可能解釋：
1. 第一次取樣時 I-8014W FIFO 是乾淨的、CPU/網路尚未進入持續高吞吐狀態，**borderline 通過了**
2. 一旦 FIFO 跑爆一次，agent 的 Stop+Clear 序列雖然執行，但**晶片內部某些狀態無法在不重開機的條件下恢復到「乾淨」**，後續取樣即使 STATUS=IDLE 也會立刻 overflow
3. 即使把 machine2 重啟、第一次能再過，也只是運氣 — 長期 24/7 連跑時必然會踩到失敗

## 3. 修正內容

### 3.1 [config.py](../pump_monitor/config.py) — 拆 RATE 為 per-machine

```python
# 之前
RATE: int = 10000

# 之後
M1_RATE: int = 10000   # 4 ch × 10 kHz = 40 kS/s 寬鬆
M2_RATE: int = 5000    # 12 ch × 5 kHz = 60 kS/s 安全帶 (低於 80 kS/s 上限 25%)
```

### 3.2 [pipeline.py](../pump_monitor/pipeline.py) — 加 err=203 重試

```python
def _capture_with_retry(ip, ch, rate, sec, rtu1, rtu2, timeout, label, max_attempts=2):
    for attempt in range(max_attempts):
        header, payload = daq_client.request_capture(ip, 9000, ch, rate, sec, rtu1, rtu2, timeout)
        if header.status == 0:
            return header, payload
        if header.error_code == 203 and attempt + 1 < max_attempts:
            log.warning("[%s] FIFO overflow (err=203), retry after 5s", label)
            time.sleep(5)
            continue
        break
    return header, payload
```

只對 FIFO overflow (203) 重試，其他錯誤（連線拒絕、bad command）不重試 — 這些通常需要運維介入而非自動恢復。

### 3.3 [config.py](../pump_monitor/config.py) — `ET_NUM_CHANNELS: 8 → 2`

現場永久只接 ch0 / ch1 兩顆 PT100，ch2~7 空接。FC04 只讀 2 個 register，`low_freq_sensor.csv` 從 11 cols 變 5 cols：

```
timestamp, pressure_motor1_bar, pressure_motor2_bar, temp_ch0_C, temp_ch1_C
```

舊 11-col CSV 已 migrate（移除 ch2~7 欄），備份為 `low_freq_sensor_8ch.csv.bak`。未來增接 PT100，把 `ET_NUM_CHANNELS` 改大即會自動加欄。

CSV 統計（與舊 mapping + 舊 RATE 對比）：

| 訊號 | 舊 (10 kHz, mapping=V×6 I×6) | 新 (5 kHz, mapping=配對) |
|---|---|---|
| machine1 V_a rms | 426 V | **428 V** ✓ |
| machine1 I_a rms | 35 A (錯標籤) | **67 A** (正確) |
| machine2 V_a rms | 50 V (錯標籤) | **27 V** (motor2 沒運轉時的 EMI) |

## 5. 副作用討論

### 5.1 Nyquist 從 5 kHz → 2.5 kHz

擔心：失去 50 Hz 工頻？**沒事**。Nyquist 2.5 kHz > 50 Hz 兩個 order，連 50 次諧波 (2500 Hz) 都剛好在邊界。

擔心：失去馬達 bearing 故障特徵？**也沒事**。Bearing 內外圈缺陷頻率多在 100~1000 Hz，遠在 Nyquist 內。

擔心：失去 VFD 載波頻率（1–3 kHz）的精確識別？**部分受影響**：
- machine1 motor1 的 VFD 載波 = 2802 Hz（前報告觀察）→ 用 5 kHz 取樣會 alias 到 5000-2802 = 2198 Hz
- 但 VFD 載波**不是訓練目標**，是雜訊源；alias 後反而被打散到別的頻率，FFT 上更難識別 — 對「以基波為主的 power signal 訓練」來說反而是好事

擔心：未來想在 ML model 加 VFD 故障特徵？**可選擇性恢復高速**：把 `M2_RATE` 暫時調回 10 kHz 跑一段時間取資料即可（已知會 hit FIFO 偶爾失敗，但配合 retry 通常仍能取到大部分 cycle）。

### 5.2 振動 / 電氣 取樣率不一致

對深度學習資料對齊有點麻煩，但兩套訊號物理意義不同（振動是 broadband 機械特徵、電氣是 50 Hz 主導 power signal），不一定要在同一 time grid 上。常見處理方式：
- **固定窗時域特徵**：對每一段 cycle，振動取 100k 列 / 電氣取 50k 列，各自抽 stat features (RMS、kurtosis、spectral peaks…) 後 concat
- **重採樣到共同 grid**：用 `scipy.signal.resample_poly` 把電氣 5 kHz 升成 10 kHz（或反向降採樣），代價是引入 reconstruction artefact

下游 ML 階段再決定。pipeline 端維持兩個原生取樣率，最大化原始訊號保真度。

## 6. 後續監控

### 6.1 機制

`pipeline._capture_with_retry` 在 err=203 時 sleep 5 秒並重試一次。實作上等於每 cycle 最多試 2 次：

- 兩次都過 → cycle wall-time ≈ 11 秒（正常）
- 第一次 203、第二次過 → cycle wall-time ≈ 27 秒（10 + 5 + 12）
- 兩次都 203 → cycle wall-time ≈ 32 秒；該 cycle 的 electrical CSV 跳過、low_freq 仍 append（NaN 在 motor2 RTU 欄；振動與壓力 / 溫度照常）

Tpoll = 600 秒，27 / 32 秒都遠小於，不影響排程。

### 6.2 觀察指標

長期跑時看 `data\logs\pump_monitor_<ymd>.log`：

```bash
grep "FIFO overflow" data\logs\pump_monitor_*.log | wc -l
grep "machine2 header status=DAQ_ERROR" data\logs\pump_monitor_*.log | wc -l
```

預期：
- 每 100 cycles 內 retry 觸發 < 5 次（< 5%）→ 健康
- > 20% cycles 觸發 → I-8014W 可能在劣化，考慮把 `M2_RATE` 再降到 4000 Hz

### 6.3 若需更高頻

未來若想恢復 machine2 高頻取樣的可行路徑：

1. **換更大 FIFO 的 ICP DAS 模組**（如 I-8017HW，FIFO 容量更高）— 需硬體採購
2. **改用兩張 I-8014W**（machine2 上裝兩張、各管 6 通道、ConfigMagicScan 平行）— 需修改 C++ agent
3. **降低每 cycle 取樣秒數**：`SEC = 5` → 12 ch × 10 kHz × 5 s = 600k 樣本，仍可能 overflow（實測 SEC=5 也失敗），所以這條路徑不通
4. **靠 retry 撐**：保留 M2_RATE=10000，純粹靠 retry 機制，但長期穩定性差

短期建議維持 M2_RATE=5000。
